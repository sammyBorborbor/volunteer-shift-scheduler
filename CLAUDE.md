## Testing

Follow **test-driven development** for new functionality: write a failing test first, implement the minimum needed to pass it, then refactor. This supersedes CONTEXT.md's original plan of a separate Phase 4 testing pass after implementation — write tests as you build, not after.

Vitest is set up (node environment, no jsdom — tests so far are pure-function unit tests, e.g. `src/lib/shiftValidation.test.ts`). Add jsdom/@testing-library only when a test actually needs to render a component; don't add it speculatively. CONTEXT.md's Phase 4 test-case list (unit/functional/integration/UAT/security) is still the reference for *what* to cover — TDD changes *when* those tests get written, not what they need to check. Supabase-integrated flows (auth, RLS-gated queries) are still verified live (Supabase MCP + Playwright against the real project) rather than mocked — this project doesn't have a local Supabase stack, and RLS/trigger behavior is exactly the kind of thing a mock would hide.

## Architecture

**Stack:** React 19 + Vite + TypeScript + Tailwind CSS v4, backed entirely by Supabase (Postgres + Auth + RLS) — there is no hand-built API layer. All data access goes through `supabase-js` directly from components/hooks, authorized by RLS policies, not application code.

**Folder layout** (feature-area organization per CONTEXT.md's NFR-06):
- `src/components/` — shared UI primitives (`Button`, `Card`, `StatusPill`, `Layout`, `FormField`, `ShiftCard`, `CoordinatorShiftRow`, `RosterEntryRow`)
- `src/pages/` — route-level views, one per use case (`Landing`, `SignUp`, `SignIn`, `AppHome`, `CoordinatorHome`, `CreateShift`, `Roster`, `MySignups`)
- `src/hooks/` — data/auth hooks (`useAuth`, `useShifts`, `useMySignups`, `useRoster`, `useMyShiftHistory`)
- `src/lib/` — `supabaseClient.ts` (the single client instance) and pure logic modules like `shiftValidation.ts`, `shiftDisplay.ts`

**Supabase wiring (`src/lib/supabaseClient.ts`):** exports `supabase` and `isSupabaseConfigured`. It deliberately never throws on missing env vars — a prior version did, which crashed the entire React tree before anything rendered (a blank page with only a console error). Any code path that touches Supabase should check `isSupabaseConfigured` and degrade to a visible status/error state, never let a missing-config error take down the whole app (NFR-04: no silent failures).

**Env vars:** must be prefixed `VITE_` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`) for Vite to expose them to the client. CONTEXT.md's own `.env.local` example omits the prefix — don't copy that naming literally.

**Database (`supabase/migrations/`):** sequentially numbered SQL files, applied directly against the live Supabase project via the Supabase MCP tools (`mcp__claude_ai_Supabase__*`) rather than the CLI. `0001_init.sql` is schema + RLS + the `sign_up_for_shift` RPC verbatim from CONTEXT.md; `0002`/`0003` harden that RPC (pinned `search_path`, revoked `anon` execution); `0004`/`0005` close a role-self-escalation hole and a signup-status-tampering hole found in a security review, plus a TOCTOU race in the RPC; `0006`/`0007` auto-create the `profiles` row from an `auth.users` trigger (no public INSERT policy on `profiles` exists — see below); `0008` computes remaining shift capacity server-side (see below); `0009` lets a volunteer sign up again after cancelling (see below). **Supabase auto-grants `EXECUTE` on new `public`-schema functions to `anon` and `authenticated` by default** — a `SECURITY DEFINER` function is silently callable by anyone unless you explicitly `revoke ... from anon`. Run `get_advisors` (security) after any migration that adds a function; don't assume the SQL in CONTEXT.md is complete as written.

**Computing remaining shift capacity (`get_upcoming_shifts_with_capacity`, `0008`):** a client-side count of confirmed `signups` per shift would be wrong for a volunteer caller — `signups_select_own_or_coordinator` only lets them see their *own* signup rows, so a naive count silently undercounts everyone else's. This function is `security definer` (like `sign_up_for_shift`) specifically to bypass that per-row RLS for the aggregate, but it only returns the computed `remaining_capacity` number — never the underlying signup rows or who they belong to. Verified live by inserting a confirmed signup from a *different* volunteer and confirming the count changed for a caller who has no RLS visibility into that row. If you add another aggregate over `signups` (e.g. a volunteer's total hours), the same undercount risk applies — don't assume a plain `select count(*)` is correct just because it works for whoever's testing it.

**Sign-up flow (`ShiftCard.tsx`):** calls `sign_up_for_shift` (built in the Step-2 era, already atomic — row-locks the shift, checks capacity and schedule overlap, inserts, all in one transaction) directly from the client and surfaces whatever error message Postgres raises (`"Shift is at capacity"` / `"Schedule conflict with an existing shift"`) — there's no client-side capacity/overlap pre-check, and there shouldn't be one; the RPC is the single source of truth and duplicating its logic client-side would just create a second thing that can drift out of sync. Because the "Sign up" button is hidden once a shift is full, the capacity-rejection path itself (as opposed to the button-hiding) can only be exercised directly against the RPC (curl/Supabase MCP), not by clicking through the UI — don't mistake "button never shows" for "capacity check untested."

**`sign_up_for_shift` re-signup after cancel (`0009`):** `signups` has a `unique (shift_id, volunteer_id)` constraint and the original RPC only ever did a plain `insert`, so a volunteer who cancelled and then tried to sign up again for the *same* shift got a raw `23505 duplicate key` Postgres error instead of succeeding — verified live before fixing it, not assumed. `0009` looks up any existing row first: a `cancelled` row gets updated back to `confirmed`; any other existing status (`confirmed`/`completed`/`no_show`) is rejected up front with `"You have already signed up for this shift"`, before the capacity/overlap checks even run. This kind of gap — two already-shipped features (sign up, cancel) that individually work but silently break when composed — is exactly the kind of bug that unit tests on isolated functions won't catch; it only shows up by actually driving the full flow end-to-end.

**Tracking a volunteer's own signup status (`useMySignups.ts`, `getShiftActionState` in `shiftDisplay.ts`):** this is *not* a boolean "signed up or not." A volunteer's own view of a shift needs to distinguish `confirmed` (can cancel), `completed`/`no_show` (read-only, past-tense — no button) and no-relationship (`open`/`full`, can sign up), because once a coordinator marks attendance the signup's status moves off `'confirmed'`. An earlier version of `useMySignups` only tracked `status = 'confirmed'`, which meant marking attendance on a still-upcoming shift made it silently look sign-up-able again — caught by actually checking the volunteer's view *after* marking attendance, not just the coordinator's roster view. `useMySignups` now returns a `Map<shiftId, AttendanceStatus>` covering `confirmed`/`completed`/`no_show` (deliberately excluding `cancelled`, which should look identical to never having signed up); `getShiftActionState(remaining, myStatus)` lets any non-null `myStatus` win over the capacity-derived `open`/`full`, regardless of how many spots are left for other people.

**Mark attendance (`RosterEntryRow.tsx`, `signups_update_coordinator` RLS):** a direct `update` on `signups`, no RPC — the coordinator RLS policy from `0004` has no `with check` restricting which status values a coordinator can set (unlike the volunteer's cancel-only policy), so it already permits `confirmed → completed`/`no_show` and corrections between them. Both "Mark completed" / "Mark no-show" buttons are always rendered, with the one matching the *current* status disabled — this lets a coordinator correct a mistake (no separate "undo" control) without inviting a redundant click-and-request on the state already showing. `useRoster` fetches `confirmed`+`completed`+`no_show` (not just `confirmed`) for exactly the reason above: filtering to `confirmed` only would make a volunteer disappear from the roster the moment their attendance gets marked.

**Role model:** `profiles.role` is `'volunteer'` or `'coordinator'`. There is no self-service coordinator signup (by design — that would be the exact privilege-escalation hole `0004` closes) and a `BEFORE UPDATE` trigger (`profiles_prevent_role_change`) blocks *any* update that changes `role`, including admin ones via direct SQL. To seed or promote a coordinator account, `alter table profiles disable trigger profiles_prevent_role_change;`, run the update, then re-enable it — don't try to UPDATE role directly, it will fail. `useAuth()` exposes `profile` (fetched from `profiles` on session change); `signIn()` returns the profile directly so callers (e.g. `SignIn.tsx`) can branch on role immediately without waiting on the hook's async state. Route protection: `ProtectedRoute` in `App.tsx` takes an optional `role` prop and redirects a signed-in user with the wrong role to *their own* home (`/app` or `/coordinator`), not to `/signin` — they're authenticated, just in the wrong place. This is a UX guard only; the real enforcement is RLS (verified live: a volunteer's direct `POST /rest/v1/shifts` gets a `403` from Postgres, independent of anything the client does).

**Nav placeholders (`Layout.tsx`):** links not wired to a real route yet use `to: '#'` and must render as a plain `<a href="#">`, not React Router's `<Link>` — `<Link to="#">` resolves relative to the *current* route (so on `/coordinator/create-shift` it silently becomes a link back to that same page), which is a real bug that shipped once already. Check `link.to === '#'` and branch, don't default to `<Link>` for everything. Also: don't add a nav item just because a role "should" have one — `coordinatorLinks` deliberately has no "Roster" entry, because rosters are per-shift and a link with no single destination is worse than no link (it'd just duplicate the logo's link to `/coordinator` under a more specific-sounding label).

**Cancel sign-up (`ShiftCard.tsx`):** a direct `update` on `signups` (no RPC) — `signups_update_own_cancel_only`'s RLS (from the `0004` security pass) already scopes this correctly: `using (volunteer_id = auth.uid() and status = 'confirmed')` `with check (... and status = 'cancelled')`, so a volunteer can only flip their *own*, currently-*confirmed* row to `cancelled`, nothing else. Verified live that attempting to set any other status (e.g. `completed`) via direct API call gets a `403` — that policy was built for a different reason (closing a self-attendance-marking hole) but happens to be exactly what cancel needs too. Cancelling sets `status = 'cancelled'`; the row is kept (audit trail), not deleted, and correctly drops out of `get_upcoming_shifts_with_capacity`'s count since that function only counts `status = 'confirmed'`.

**Roster (`useRoster.ts`, `Roster.tsx`):** needed no new migration — `signups_select_own_or_coordinator`'s RLS already grants a coordinator full visibility into every signup (that policy exists for exactly this), so the roster is a plain `select ... signups joined to profiles`, unlike the volunteer-facing capacity count which specifically has to bypass RLS. Uses `.maybeSingle()` for the shift lookup, not `.single()` — `.single()` throws a raw, unfriendly PostgREST error ("Cannot coerce the result to a single JSON object") on a bad/deleted shift ID instead of a clean "not found" state; `.maybeSingle()` just returns `null` and lets the page render a proper message.

**Design tokens (`src/index.css`):** Tailwind v4 `@theme` block, semantic (not literal) color names — `ink`/`ink-foreground`, `accent`/`accent-foreground`, `surface`/`surface-elevated`, `muted`, `border`, plus `success`/`warning`/`destructive`/`neutral` pairs (each a light background + a matching darker text color, tuned for ≥4.5:1 contrast — don't pair an accent background with white text without checking contrast first, e.g. white-on-`accent` is ~1.7:1). Single font family (Inter) throughout — intentional for this app-UI/product register, not an oversight.

**Should-have: coordinator under-capacity signal (FR-11, `getSignupProgress` in `shiftDisplay.ts`, `CoordinatorShiftRow.tsx`):** the volunteer-facing "spots left" framing (`getCapacityStatus`) is the wrong metric for a coordinator — a shift with 1 spot left out of 10 reads as "urgent" to a volunteer but is a healthy, well-subscribed shift from the coordinator's side. `getSignupProgress(capacity, remaining)` flags the opposite condition instead: a `confirmed/capacity` fill rate below 50% renders as a warning ("X/Y signed up"), since that's what actually needs the coordinator's attention (promote the shift, recruit more people). `CoordinatorShiftRow` was previously using `getCapacityStatus` — same bug shape as reusing an admin's `useMySignups` boolean for coordinator views; the two roles need different derived signals from the same raw numbers, not the same badge relabeled.

**Should-have: volunteer's own shift history (FR-09, `useMyShiftHistory.ts`, `MySignups.tsx` at `/app/my-signups`):** unlike every other signup query in the app (`useMySignups`, `useShifts`, `useRoster`), this one deliberately has **no date filter and no status filter** — the whole point of the page is showing a volunteer's full history, including past shifts and cancelled signups, which every other view intentionally excludes. This needed a separate `SignupHistoryStatus` type (`AttendanceStatus | 'cancelled'`) and `getSignupHistoryStatus()` rather than widening `AttendanceStatus` itself, since every other caller of that type intentionally never sees `'cancelled'` (it means "free to sign up again" everywhere else) and shouldn't have to add a dead branch for it. `isUpcoming(date)` splits entries into "Upcoming"/"Past" sections client-side using the same "today counts as upcoming" convention as `shiftValidation`'s date rule, rather than a second RPC.

**Component classNames can't safely override each other's baked-in Tailwind classes.** `Button` and `Card` both hardcode classes (e.g. `Card` always has `p-5`) *before* splatting in the caller's `className`, so `<Card className="p-0">` produces `"... p-5 ... p-0"` in the DOM — which one wins depends on Tailwind's generated CSS order, not attribute order, and is not something to rely on. This has already caused two real bugs (a `Button` `ghost` variant that wouldn't recolor on the dark landing hero; wanting a padding-less `Card` for the roster list). The fix both times was the same: don't fight it, just use a plain element with the exact classes needed instead of the shared component when the override isn't a simple additive one (spacing/layout classes on top are fine; overriding a property the component already sets is not).
